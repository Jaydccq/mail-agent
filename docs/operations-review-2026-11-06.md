## 建议，按优先级排列

### 1. 显式记录并报告分析降级，设计有边界的恢复处理

11 月 3 日晚 Codex 出现 27 次失败调用，9 封邮件发生流水线重试，其中 8 封最终使用模板。至少两次日志明确显示本地模型端点返回 HTTP 426；其他日志被 CLI 启动信息占据并截短，不能把全部失败归为同一原因。目前实时调用和后续实际邮件分析均已恢复。

8 封模板邮件均没有关联待办，其中 6 封的时间信号 has_time ≥ 0.5。模板分析返回空 deadlines，邮件仍被标记 done，所以恢复后不会自动重做分析。这是“潜在日期未提取”的风险，不能据此认定确有 6 个截止日期遗漏。

建议：保持通知可及时发出，同时将生成分析降级作为可查询状态；持续失败或恢复时给一次去重健康提醒；如需恢复提取，使用明确的重分析状态并按邮件去重待办与通知。先用合成邮件覆盖“失败→恢复→只生成一次待办、通知不重发”的回归，再处理真实历史邮件。

相关：`src/mailagent/ai/analyze.py:244`、`src/mailagent/agent/pipeline.py:160`、`src/mailagent/db.py:400`。另外，CLI 错误日志应保留脱敏后的最终错误类型，而非只截取开头的启动横幅。

### 2. 给同一会话的密集通知增加合并策略

11 月 5 日共 40 封邮件触发 notify，其中同一发件人的 4 个会话占 35 封。消息 ID 没有重复，现有证据不支持“同一封邮件重复处理”；更像每条会话更新分别通知。

建议：先用合成邮件验证按会话短时间合并通知，保留最新状态与新增事项，并明确重要安全事件、VIP 或紧急事项的处理规则。没有用户偏好依据前，不直接静音发件人或提高全局通知门槛。

相关：`src/mailagent/agent/pipeline.py:48` 及逐封通知入队逻辑。

### 3. 修正健康状态的含义与退出码

`last_sync_at` 在连接成功时更新，后续正常收信和推进游标不更新它。本次用内存数据库和合成邮件重现：08:00 连接、10:00 成功入库后，last_uid 和 updated_at 已推进，last_sync_at 仍停在 08:00。它不能可靠表示“最后一次成功同步”，也不能直接作为停摆告警依据；updated_at 又可能来自 Sent 轮询，不能直接替代 INBOX 心跳。

此外，doctor 末尾只展示后台服务状态，不把“服务未运行”计入失败次数；其他依赖检查通过时仍可能输出 All good 并以 0 退出。这是源码确认的健康检查缺口，本次实际服务是运行中的。

建议：区分“上次成功检查收件箱”和“上次收到新邮件”，按可验证的时间语义更新状态；doctor 对后台未运行返回非零。回归覆盖“无新邮件但同步正常”和“依赖正常但守护进程停止”。

相关：`src/mailagent/mail/watcher.py`、`src/mailagent/db.py:295`、`src/mailagent/db.py:334`、`src/mailagent/cli.py:826`。

### 4. 控制待办噪声并保留用户决定

当前 130 条待办均为 open，其中 29 条日期已过去，7 条日期是今天。newsletter、shopping、promotion 分类邮件合计产生了 16 条待办；这不证明它们都不需要行动，但值得抽样检查。当前摘要包含过期未完成项，旧项可能持续占用摘要空间。

建议：提供过期待办复核或归档入口，区分实际需要用户行动的日期与一般资讯活动；不要未经确认批量完成、删除或重排已有待办。

相关：`src/mailagent/agent/scheduler.py:181`。

### 5. 补充 SQLite 备份与恢复验证

项目内未见邮件数据库的自动备份及恢复流程；没有检查或否定系统级 Time Machine 等备份。邮箱正文可以重新搜索，但本地规则、记忆和待办状态不能依靠 Gmail 自动恢复。

建议：采用 SQLite backup API 制作一致性快照，设置权限与保留策略，并在副本上验证恢复。运行中直接只复制 agent.db 会遗漏 WAL 中尚未合并的事务。
